## 一、Shannon 的路由策略(从前端到后端)

### 整体流程图

```
HTTP POST /api/v1/tasks
    │
    ▼
Gateway 处理器 (task.go:506)
    │  1) 解析 Query/Session/Context
    │  2) 注入模板、技能、模型覆盖等
    │  3) 应用策略预设 (research_strategy)
    │
    ▼
gRPC → OrchestratorService.SubmitTask (service.go:236)
    │  根据 labels 选择入口:
    │    - workflow=supervisor → SupervisorWorkflow
    │    - workflow=simple    → SimpleTaskWorkflow
    │    - 默认                → OrchestratorWorkflow
    │
    ▼
OrchestratorWorkflow (orchestrator_router.go)
    │
    ├── 早退路径(跳过 LLM 分解):
    │    • 模板请求        → TemplateWorkflow
    │    • skip_synthesis  → SimpleTaskWorkflow
    │    • force_swarm     → SwarmWorkflow
    │    • force_research  → ResearchWorkflow
    │
    ├── 调用 DecomposeTask (Python /agent/decompose)
    │    → 返回 complexity_score, mode, subtasks, cognitive_strategy
    │    → 失败时:强制 score=0.1 走 SimpleTaskWorkflow
    │
    ├── 预算预检 + 审批门控
    │
    └── 策略分发(orchestrator_router.go:855-1109):
         • role=browser_use         → BrowserUseWorkflow
         • auto-detect 浏览器意图   → BrowserUseWorkflow
         • cognitive_strategy 命中  → React/Research/Exploratory/Scientific
         • isSimple (complexity<0.3) → SimpleTaskWorkflow
         • 默认                     → DAGWorkflow
```

### Shannon 怎么判断"简单"还是"复杂"?

**关键点:复杂度分析不是由 Go 编排器自己完成,而是通过 gRPC 调用 Python LLM 服务,由 LLM 评分。**

#### 1. 主要路径:LLM 评分

在 `decompose.go:49-116` 处的 `DecomposeTask` 活动向 Python 服务发起 POST 请求:

```
POST ${LLM_SERVICE_URL}/agent/decompose
```

`python/llm-service/llm_service/api/agent.py:3785-4621` 的 `decompose_task()` 实现了 LLM 评分。系统提示词明确指示:

> "For SIMPLE queries ... set `complexity_score < 0.3` and provide a single subtask.  
> For COMPLEX queries ... set `complexity_score >= 0.3` and decompose into multiple subtasks."

LLM 返回 `DecompositionResponse`,包含:

- `mode`: `simple` / `standard` / `complex`
- `complexity_score`: 0.0 - 1.0
- `cognitive_strategy`: `direct` / `decompose` / `exploratory` / `react` / `research` —— **这是路由决策的关键信号**
- `execution_strategy`: `parallel` / `sequential` / `hybrid`

#### 2. 阈值定义(权威来源)

`config/features.yaml:84-91`:

```yaml
workflows:
  complexity:
    simple_threshold: 0.3 # < 0.3 = 小模型
    medium_threshold: 0.5 # 0.3-0.5 中型, > 0.5 大型
  dag:
    simple_threshold: 0.3
```

#### 3. `isSimple` 的最终计算逻辑

`orchestrator_router.go:856-872`:

```go
needsTools := <任何子任务有 SuggestedTools / Dependencies / Consumes / Produces / ToolParameters>
simpleByShape := len(decomp.Subtasks) == 0 ||
                 (len(decomp.Subtasks) == 1 && !needsTools)
isSimple := decomp.ComplexityScore < simpleThreshold && simpleByShape
```

也就是说,**单纯分数低于 0.3 还不够**,子任务必须 ≤ 1 个且不需要工具/依赖,才走 `SimpleTaskWorkflow`。

#### 4. 失败回退

- **Python /agent/decompose 失败**:`orchestrator_router.go:684-714` 合成 `complexity=0.1` 的最小响应 → 强制走 `SimpleTaskWorkflow`。
- **早期路径失败**:`AnalyzeComplexity` 活动 (`analyze.go:10-13`) 只是一个转发到 `DecomposeTask` 的兼容层。

#### 5. 备用启发式(未走主路径)

`python/llm-service/llm_service/api/complexity.py:41-114` 有规则式 `_heuristic_analysis()`(基于关键词 `what is`/`analyze`/`implement`、查询长度、工具数),**但这个端点不在主路径上**,仅作为独立工具 API 暴露。

## 二、右侧"思考过程"面板的实现

这个面板的真实名字叫 **EXECUTION TIMELINE**(执行时间线),位于 `run-detail/page.tsx:2296-2352`。

### 整体结构

```
┌──────────────────────────────────────────────────────┐
│  EXECUTION TIMELINE               ↻ Reconnecting... │  ← 头部
│ ┌──────────────────────────────────────────────────┐ │
│ │     ⊙  agent-3 ←─ (5)──────                     │ │
│ │  ╱        ╲                                       │ │  ← RadarCanvas 雷达图
│ │ agent-1     agent-2                               │ │     (160px 高)
│ │  ╲        ╱                                       │ │     30Hz 动画
│ │     ⊙ ← center: 任务完成                          │ │
│ └──────────────────────────────────────────────────┘ │
│ ──── Task Board (仅 swarm 模式): 3/7 done ── ────  │  ← SwarmTaskBoard
│ ●  Agent is reasoning                12:34:01        │  ← RunTimeline
│ │  { "role": "generalist", ... }                     │     时间线条目
│ ●  Tool Called: web_search           12:34:02        │
│ ◐  Tool Result: Found 5 results     12:34:03        │
│ ●  Data Processing: Combining...     12:34:05        │
└──────────────────────────────────────────────────────┘
```

**不是简单的文字流**——它由 3 层组成:

1. **顶部雷达图**(Canvas 动画)
2. **中间任务板**(仅 swarm 模式)
3. **底部事件时间线**

### 思考过程是怎么"实时"传到前端的?——SSE

**传输协议是 Server-Sent Events (SSE)**,不是 WebSocket(虽然后端也实现了 WS,但前端不用)。

#### 后端流式管线

```
[Temporal Workflow 内部]
  ↓ 各种 EmitTaskUpdate 调用
  activities/agent.go, synthesis.go, react.go ...
  ↓
[Go: streaming/manager.go]
  - Event 结构(workflow_id, type, agent_id, message, payload, timestamp, seq)
  - XAdd 写入 Redis Stream: shannon:workflow:events:<workflowID>
  - 24h TTL,容量 256
  - 终态事件也写入 shannon:notifications:global 用于 webhook
  - 关键事件持久化到 PostgreSQL event_log 表
  ↓
[Go: httpapi/streaming.go] SSE 端点
  - GET /api/v1/stream/sse?workflow_id=<id>
  - 支持 Last-Event-ID 断点续传
  - 支持 ?types=A,B,C 服务端过滤
  - 内部事件名重命名为 OpenAI 风格:
      LLM_PARTIAL      → thread.message.delta
      LLM_OUTPUT       → thread.message.completed
      ERROR_OCCURRED   → error
      STREAM_END       → done
  - 每 10 秒发心跳 : ping
  - 30 秒首事件超时(workflow 不存在则发错)
  - 完成后 30 秒无新事件则关连接
  ↓
[HTTP/SSE]
  ↓
[浏览器 EventSource]
```

#### 前端订阅

`desktop/lib/shannon/stream.ts:19-282` 的 `useRunStream()` React Hook:

```ts
const es = new EventSource(`${API_BASE_URL}/api/v1/stream/sse?workflow_id=${id}`);
es.addEventListener('thread.message.delta', (e) => {
    // token 级 delta,进入 DeltaBuffer
    deltaBuffer.set(streamId, { delta, ... });
});
es.addEventListener('TOOL_INVOKED', ...);
es.addEventListener('AGENT_THINKING', ...);
// ... 47 种事件类型
// 然后 requestAnimationFrame 内一次性 dispatch 到 Redux
```

**关键技巧:delta 合并**(`stream.ts:28-46, 121-125`)

LLM 的 token 流是高频小块,直接 dispatch 会把 Redux 搞爆。所以前端把同一个 `streamId` 的 delta 缓存在 `Map` 里,在 `requestAnimationFrame` 里统一刷新一次,实现**~60fps 的平滑打字效果**。

**重连**(`stream.ts:249-261`)

指数退避:`BASE_RECONNECT_DELAY_MS * 2^attempt`,上限 10 秒,最多 10 次。用 `lastEventId` 续传丢失事件。

### "思考到什么程度"是怎么算出来的?——事件驱动

每个事件都是一个真实的工作流事件,被分类成 4 大类(`run-detail/page.tsx:1410-1416`):

| 分类       | 触发事件类型                        | 图标色 |
| ---------- | ----------------------------------- | ------ |
| **agent**  | 含 AGENT, DELEGATION, TEAM, ROLE    | 蓝/绿  |
| **llm**    | LLM\_\*, `thread.message.completed` | 紫     |
| **tool**   | 含 TOOL                             | 橙     |
| **system** | 其他                                | 灰     |

**状态推断**(`run-detail/page.tsx:1419-1429`):

- `STARTED`, `AGENT_THINKING`, `WAITING`, `APPROVAL_REQUESTED` → **running**(动画脉冲)
- `COMPLETED`, `OBSERVATION` → **completed**(绿勾)
- `ERROR_OCCURRED`, `WORKFLOW_FAILED` → **failed**(红警)

**友好标题映射**(`run-detail/page.tsx:1470-1539`):

把后端的 `"Thinking: REASON..."` 翻译成前端的 `"Agent is reasoning"`,`"Thinking: ACT..."` → `"Agent is planning action"` 等。

### "仪表盘"那部分是什么?——是雷达图

**严格意义上没有传统图表库**(没 Recharts/Chart.js/D3),仪表盘效果来自**自绘 Canvas 雷达图**:

- `desktop/components/radar/RadarCanvas.tsx` — 2D Canvas 渲染
- `desktop/components/radar/RadarBridge.tsx` — Redux 事件 → 雷达 store(zustand)
- `desktop/lib/radar/store.ts` — `applyTick({tick_id, items, agents, metrics, ...})`
- `desktop/lib/radar/types.ts:35-42` — 类型定义(含 `active_agents, total_tokens, total_spend_usd, live_tps, live_spend_per_s, completion_rate`)

**每个 agent 是一架"小飞机"**,从外圈飞向中心,完成时脉冲一下消失。Lead Agent 决定时会有金色脉冲。

**30Hz 渲染**(`RADAR_REFRESH_HZ=30`),飞行动画有缓动,完成时加速到 2 秒内抵达中心(`RadarBridge.tsx:263-301`)。

> **注意**:`ProjectMetrics` 类型已定义且 `applyTick` 接受 `metrics` 字段,但 `RadarBridge` 目前**没真正发 metrics**——只发 `items` 和 `agents`。这是预留的扩展点,未来可以加真实数字仪表盘。

### 状态药丸(Inline Status Pill)——左栏的"动态进度条"

`runSlice.ts:138-155` 的 `STATUS_EVENT_TYPES` 集合决定哪些事件在**左栏对话区**显示为短小的"药丸"状态条:

```
[Agent is reasoning]   ← AGENT_THINKING (但仅在 isShortStatusMessage < 150 字符)
[Tool Called: web_search]  ← TOOL_INVOKED
[Combining findings from 3 agents]  ← DATA_PROCESSING
[Needs approval: ...]  ← APPROVAL_REQUESTED
[Task budget at 85.0%]  ← BUDGET_THRESHOLD
```

长 LLM 推理内容被过滤掉(`isShortStatusMessage` `runSlice.ts:191-200`),只显示短状态。

**自动滚动**:`run-detail/page.tsx:1660-1725`,用户在底部时 `requestAnimationFrame` 滚到底;用户向上滚则不动。

## 总结一句话

1. **路由**:Shannon 用一个**专用的 LLM 分解调用**(`/agent/decompose`)同时拿到 `complexity_score` + `cognitive_strategy` + 子任务列表,Go 路由器按分数(< 0.3)与认知策略把请求分发到 16 种工作流中的某一种(Simple/DAG/React/Research/Exploratory/Scientific/Browser/Swarm/Template/Schedule/...),失败时强制退化为 Simple。
2. **右侧思考面板**:本质是 **SSE 事件流** 把后端 47 种工作流事件实时推到浏览器,通过 **Redux + React + 30Hz Canvas 雷达** 三层叠加实现"动态思考可视化"。
